# 实测基准：落位率与 panic 率（v1.0.17 参数调优）

> 数据来源：HONOR MLY-AN00 / MagicOS 11.0.0.110 / kernel `6.12.58-android16-6-g3a7ac1674240-abogki541502914-4k`。
> 全部为真机实测，非推算。统计口径见文末「方法与可复现」。

## 0. 结论速览

| 指标 | 改前（`PRE_PIPES=20000`） | 改后（`PRE_PIPES=512`） |
|---|---|---|
| 落位成功（拿到泄漏页） | **62%**（16/26） | **80%**（37/46） |
| panic（内核重启） | 12% | 7% |
| 平均开打温度 | 28°C | 28°C |

改后那 80% 是两组独立复现的合并：88%（23/26）与 70%（14/20）。
**样本量会影响结论强度**——单看第一组会高估到 88%，这正是为什么要求每配置 ≥20 发。

只改了一个参数，其余全部保持原值。

## 1. 背景：为什么会有这个参数

exploit 里有一条「512KB 管道载体」路径（`PIPE512`），用来接住被释放的 slab 页。
它的第一步是 `fcntl(fd, F_SETPIPE_SZ, 512*1024)`。

但 Linux 对管道页做**按 uid 记账**：

```
/proc/sys/fs/pipe-user-pages-soft = 16384 页 = 64MB
```

一旦某个 uid 的管道页用量超过这个软上限：

- 新建的 pipe 只给最小容量（2 页 / 8KB）
- **`F_SETPIPE_SZ` 一律返回 `EPERM`（errno=1）**

而 exploit 默认会先预建 20000 个 pipe（`P645_PRE_PIPES=20000`）占住竞态窗口。
20000 个 pipe 早就把 64MB 预算吃光，于是——**512KB 管道载体从未生效过**。

### 直接证据

历史上 62 份真机运行日志里，这一行**无一例外**：

```
v8_pipe first F_SETPIPE_SZ=-1 (want 524288) errno=1
```

设备上跑 `pipetest`（aarch64 静态小程序）复现：

| 已持有 pipe 数 | 新建 pipe 设 512KB |
|---|---|
| 0 | **成功**（524288） |
| 8000 | **EPERM**，且新 pipe 只有 64KB |

## 2. A/B：`PRE_PIPES` 20000 vs 512

- 两臂其余 env 与 App 的 permissive 阶段**逐字相同**（直接调 `./x645`，绕过 UI）
- 交替执行，抵消温度/开机时长漂移；每发前等温度 ≤42°C
- 臂别验证：A 臂日志 `F_SETPIPE_SZ=-1`，B 臂 `=524288` —— 确实走不同代码路径

| 臂 | `PRE_PIPES` | n | 落位成功 | panic |
|---|---|---|---|---|
| A | 20000 | 26 | 16（62%） | 3（12%） |
| B | 512 | 26 | 23（88%） | 1（4%） |

后续又用独立批次复现 `512`（网格 C1 组 + 决赛 F_C1 组，共 20 发）得 **14/20 = 70%**。
合并 `512` 两组：**37/46 = 80%**。两比例 z 检验 `z ≈ 2.0`（双侧 `p ≈ 0.045`）。

**教训**：第一组 88% 里有运气成分；不补第二组就会把结论写成"90%"，实际是 80%。

## 3. 参数网格（每配置 6 发，25–32°C）

| 配置 | 说明 | n | 落位成功 | panic |
|---|---|---|---|---|
| `PIPE512=128` | 管道载体 64→128 条 | 20 | 17（85%） | 2（10%） |
| **基准（`PRE=512`）** 网格组 | — | 6 | 5（83%） | 1（17%） |
| `THRESH=16` | 阈值收紧 | 6 | 5（83%） | 1（17%） |
| `DEL_RUN_MS=1500` | delete 相位缩短 | 6 | 5（83%） | 0 |
| `PRE_PIPES=0` | 完全不预建 | 6 | 5（83%） | 0 |
| `THRESH=64` | 阈值放宽 | 5 | 4（80%） | 0 |
| `PRE_PIPES=2048` | 中间值 | 5 | 4（80%） | 0 |
| `PRE_PIPES=0` + `PIPE512=128` | 组合 | 20 | 13（65%） | 3（15%） |
| `PIPE_K=2` | 喷页系数减半 | 6 | 4（67%） | 1（17%） |
| `ANON2_MB=1536` | anon 喷页 +50% | 6 | 4（67%） | 1（17%） |
| `NDEL=5` | delete 线程 7→5 | 6 | 4（67%） | 1（17%） |

### 三条读出来的规律

1. **`PRE_PIPES` 只有 ≤512 可用**（硬边界，不是调优偏好）：

   | `PRE_PIPES` | `F_SETPIPE_SZ` | 落位 |
   |---|---|---|
   | 0 | 524288 ✓ | 83% |
   | 512 | 524288 ✓ | 86–90% |
   | 2048 | **-1** ✗ | 80% |
   | 20000 | **-1** ✗ | 63% |

   `2048 × 8 页 = 16384`，正好等于软上限，撞得很干脆。

2. **`PIPE512` 64→128 没有增益**（85% vs 86%）。之前的 "6/6 全中" 是小样本运气，
   补到 20 发后回到与基准相同。**不做无依据的改动**。

3. **喷页量存在最优区间**：`PIPE_K=2`（太少，67%）和 `ANON2_MB=1536`（太多，67%）都变差。
   喷得少接不住释放页；喷太猛会挤压管道页预算、拉长窗口。

## 4. 温度的影响（这一项比参数更大）

同一套参数，只改温度：

| 条件 | 落位成功 | panic |
|---|---|---|
| 冷机 25–32°C（本次 A/B，53 发） | 63–90% | **5–6%** |
| 热机 46–48°C（历史 62 份日志） | 37% | **38%** |
| 63°C（历史记录） | 0%（`leak=0`） | — |

结论：**panic 主要是温度驱动，不是参数**。所以 App 里同时做了：

- 严格温度闸（>44°C 先等降温，最多 3 分钟）
- 运行时把屏幕压到最暗（屏幕是 SoC 之外最大的热源，1 档 vs 中高亮差 2–3°C）
- 每发记录 `meta.log`（温度 / 频率 / 充电 / 内存），便于事后归因

## 5. 温度：现有数据**不能**支持"越热越差"

> 本节在 2026-10-27 被重写。原版写的是「冷机 80% → ≥50°C 42%」「panic 主要是温度驱动」，
> 经独立复核**这两条都不成立**，原因见下。保留这段历史是为了不让同错误再犯。

### 5.1 全部可解析数据（179 发）按开打温度分桶

| 温度桶 | n | 落位成功 | panic |
|---|---|---|---|
| <35°C | 147 | 107（73%）| **15（10.2%）** |
| 35–39°C | 7 | 7（100%）| 0 |
| 40–44°C | 3 | 2（67%）| 0 |
| 45–49°C | 3 | 3（100%）| 0 |
| ≥50°C | 19 | 18（95%）| 0 |

**全部 15 次 panic 都发生在 ≤34°C**；≥35°C 的 32 发一次 panic 都没有。

### 5.2 原版数字错在哪（两个具体 bug）

**① 「≥50°C 只有 42%」= 记账错误。**
那个 42% 是 8/19。可"19"里含 11 行被脚本标成 `SKIP_boot`（因 `uptime<120s`）而丢弃的记录——
**这 11 行里有 10 行其实落位成功**（正文是 `stage_done st=0 try=N leak=0x…`）。
如实计入是 **18/19 = 95%**，且该组 0 次 panic。

**② 「84–88°C 仍能命中」= 温度标签不可信。**
`ab_hot3` 那 20 行里，`t0` **每一行**都比同次的 `t1` 高 17–56°C（中位 35°C）——
两者不可能同时是同一个 SoC 的温度。原因：`t0` 是在 `ab_one.sh` 的 **8 线程人工烤机循环之后**
立刻读的，不是载荷竞态窗口内的温度。所以"84–88°C 命中"里的**命中是真的，温度是假的**。

**③ 「panic 主要是温度驱动」= 无证据。** 见 5.1，方向甚至相反。

### 5.3 那 62 份历史日志（37% panic）不能归因给温度

- 62 个文件里**完全没有温度字段**（对它们 grep `temp=|thermal_zone|z0a=|die0=|t0=` 全部 0 命中；
  注意裸 `temp` 会误命中 `attempts=`）。
- 它们 37% 的 panic 是真的，且与今天 A 臂（`PRE_PIPES=20000`）的 12% 显著不同（p≈0.021）。
- 但**没有温度证据**。第一嫌疑改回 **doze/屏幕状态**（项目文档里有独立 A/B 硬证：Dozing → 0/N，
  Awake+stayon → 4/5）与 **boot 新鲜度**、以及 `NDEL=6`（旧）vs `7`（新）的漂移。

### 5.4 仍然成立的结论

- **`PRE_PIPES` 20000 → 512：落位 62% → 80%**（冷机，A/B 各 26 发，p≈0.045）。这条与温度无关，是参数结论。
- 温度与结论在当前数据里**共线**：高温样本几乎全来自后期的 `PRE_PIPES=512` 组，
  所以"热端落位更高"也**不能**解释成"加热更好"——这是混杂，不是因果。

### 5.5 由此得到的正确做法

温度闸保留，但**定位改成"经验性保守措施"而不是"数据驱动"**：

- 没有证据表明 45–50°C 会显著变差，所以闸门不该让用户白等太久（中等档 3 分钟已足够）
- 但有明确证据表明**排除法还没做完**：要判定温度到底有没有影响，必须做
  **外部加热 + 同配置冷/热交替**的实验（不能用 CPU 烤机，否则烤机本身改变竞态环境）

### 5.6 待做：决定性实验（已设计，未执行）

1. **开机后温度曲线标定**（10 分钟）：确认"刚重启 1–2 分钟内读数是假的"这个伪影的边界。
2. **外部加热对照**（约 40 分钟）：吹风机/暖宝宝把机身加到 45–50°C，与冷机**交替**各 20 发，
   同配置、`uptime>600`、孤儿进程清零、三种温度读数（`z0` / `die` / 电池）同时记录。
   判据事前写死：若热组落位率显著低于冷组且 panic 更多 ⇒ 温度有害；否则撤销该假设。

## 6. 方法与可复现

设备端直接调用原生载荷（与 App 同一套 env，只是绕过 UI）：

```bash
cd /data/local/tmp/rk && env \
  P645_STAGE=1 P645_STAGE_FROM=0 P645_STAGE_TO=1 P645_STAGE_TRIES=4 P645_ATTEMPTS=1 \
  P645_TIMERS=54000 P645_REPEATS=520 P645_NDEL=7 P645_DEL_RUN_MS=2500 \
  P645_CONC=1 P645_ANON_MB=8 P645_FREEZE=1 P645_V8=1 P645_ANON2_MB=1024 \
  P645_PIPE512=64 P645_PIPE_K=4 P645_MODE=4 P645_THRESH=32 P645_SCAN_STOP=1 \
  P645_FORCE_LEFT=0xffffff8049fe7a59 \
  P645_PRE_PIPES=512 P645_LOG=/data/local/tmp/rk/ab.log \
  ./x645
```

判定（读日志尾部）：

| 日志尾部 | 归类 |
|---|---|
| `stage_all_done` + `leak=0x…` | 落位成功 |
| `stage_all_done` + `leak=0` / `stage0_failed_no_leak` | 未命中 |
| `v8_reaping victim=…` 之后无输出 | panic（kill 相位） |
| `concurrent spray start …` 之后无输出 | panic（喷页相位） |

跑完脚本会 `setenforce 1` 复位 SELinux，保持两臂条件一致。
每轮记录温度、`F_SETPIPE_SZ` 返回值、充电状态与 CPU 频率。

## 7. 一个必须记住的坑

`F_SETPIPE_SZ` 的 EPERM **不会报错到 UI**，只会让载体静默退化成 8KB 小管道。
如果没有对着 `v8_pipe first F_SETPIPE_SZ=` 这一行做核对，很容易把它当"正常现象"，
然后再去调其他参数——方向从一开始就是错的。

## 8. 耗时（真机实测）

### 8.1 单发

| 环节 | 冷机实测 | 说明 |
|---|---|---|
| 单发端到端（含设备端一次往返） | **53s** | `ab_one.sh`：测温→跑载荷→采样→复位 SELinux 一次做完 |
| 单发端到端（旧脚本，10 次 adb 往返） | **87s** | 每次 adb 往返约 1.0s，10 次就是 10s 纯开销 |
| 载荷内部的 delete 相位 | **2.5s** | `deletes_done - timers_created`，与 `DEL_RUN_MS=2500` 吻合 |
| 每次内部重试的增量 | **21–22s** | 同一次运行里连续三轮 `timers_created` 的间隔：37.4 → 59.5 → 80.8 → 102.3s |

**推论**：`try` 序号直接决定单发耗时。`try=0` 约 50s，`try=3` 要约 105s。
这也解释了为什么"热机时整体变慢"——不是每发更慢，而是失败/重启的比例上去了。

### 8.2 panic 的代价

| 环节 | 实测 |
|---|---|
| 内核 panic → adb 恢复可用 | **~90s** |
| 之后 `pm install -r` 重装 | **~30s** |
| 合计 | **≥2 分钟**（还不含用户手动操作） |

这就是"等满 3 分钟仍 >55°C 时直接放弃本轮"的依据——**放弃的成本远低于崩一次**。

### 8.3 整条链

App 里一次完整跑链包含：permissive（1–3 发）→ phase1（1 发起）→ phase2（1 发起）
→ 加载模块 → 等 KernelSU 自加载（最多 24s）→ su 验证。
冷机顺利时约 3–5 分钟；中途任何一步 panic 都要重新开始。

### 8.4 事后怎么复盘时间

每发开打前会往 `/data/local/tmp/rk/meta.log` 追加一行：

```
stage=phase1 temp_mc=44100 uptime=812 memfree=7310452 procs=1017 cpu=2496000 chg=Full ts=20:41:03
```

配合原生载荷自己的日志（`stage_done st=0 try=N leak=0x…`），可以还原每次运行的时间线。

## 9. phase1 / phase2：真机 5 轮全链（2026-10-27，mac adb 直跑，不经 App UI）

> 本节重写过。原版写「phase1 落位 47%、phase2 44%、panic 32–44%」，
> 那份统计来自设备上未保存的日志，且当时的测试脚本有两个致命缺陷（见下），数据作废。

### 9.1 结果

| 轮 | 结果 | permissive | phase1 | phase2 | 耗时 |
|---|---|---|---|---|---|
| 1 | ROOT_NOSU（su 失败=脚本 bug）| try1 | **try1** | **try1** | 233s |
| 2 | **ROOT** | try1 | **try1** | **try1** | 157s |
| 3 | **ROOT** | try1 | **try1** | **try1** | 222s |
| 4 | FAIL_P1（P1 连 miss 3 次）| try1 | × | × | 154s |
| 5 | PANIC_PERM（真 panic，38°C）| × | — | — | 69s |

- **P1 到达后一发命中：3/4**；**P2 一发命中：3/3**
- **panic：1/5（20%），发生在 permissive 阶段、起步 38°C**
- 完整成功（root + KSU + su）：2/5；修掉 su 那个脚本 bug 后是 **2/3**

### 9.2 原版数据为什么作废（两个脚本 bug）

1. **每发后 `pkill -9 -x pc`**：`pc` 不只是 perf 探针，它是**判据生产者**（`CAPBND_ZERO`/`CAPEFF_OK`/`ROOT_OK`
   都是它打印的）**兼模块加载者**。把它杀掉 ⇒ 即使写成功也拿不到 verdict ⇒ 全被记成 "miss/FAIL"。
   证据：某轮 `c2` 日志 `stage_done st=1 try=0 leak=0x… tgt=…` 命中候选 idx=1，
   而 `probe.log` 最后一行是 `Killed`。
2. **漏传 `P645_CONC=1`**（源码默认 0）：不预建管道、不启并发喷页 ⇒ 512KB 载体无从生效 ⇒
   落位必败。那一批 4 轮全部 panic，被我误读成"P1 很难"。

### 9.3 由此得到的判断

- **P1/P2 不是瓶颈**。它们的落位层与 permissive 是同一段代码，参数也已经验证过；
  在 37–42°C 下同样是一发命中。
- **P1 的真正失败模式是"没写到被判据认到的 cred 上"**（第 4 轮连 miss 3 次），
  与温度、与落位成功率无关。下一步该查候选 cred 的**选取顺序**（App 用 probe 输出前 8 个，
  测试脚本按 cap 位权重自己排序）。
- **panic 与温度无关**：这次 20% 的 panic 发生在 38°C，而 179 发历史数据里 15 次 panic
  全部 ≤34°C（见 §5）。

### 9.4 顺带改的产品行为

P1/P2 前的温度闸改成**宽松档**（>48°C 才等、60s 封顶、>58°C 放弃）：
既然 P1/P2 在 37–42°C 本来就是一发命中，按用户档位长等只是白拖 1–4 分钟。
