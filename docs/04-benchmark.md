# 实测基准：落位率与 panic 率（v1.0.17 参数调优）

> 数据来源：HONOR MLY-AN00 / MagicOS 11.0.0.110 / kernel `6.12.58-android16-6-g3a7ac1674240-abogki541502914-4k`。
> 全部为真机实测，非推算。统计口径见文末「方法与可复现」。

## 0. 结论速览

| 指标 | 改前（`PRE_PIPES=20000`） | 改后（`PRE_PIPES=512`） |
|---|---|---|
| 落位成功（拿到泄漏页） | **62%**（16/26） | **80%**（37/46） |
| panic（内核重启） | 12% | 7% |
| 平均开打温度 | 28°C | 28°C |

改后那 80% 是两组独立复现的合并：88%（23/26）与 70%（14/20）。
**样本量会影响结论强度**——单看第一组会高估到 88%，这正是为什么要求每配置 ≥20 发。

只改了一个参数，其余全部保持原值。

## 1. 背景：为什么会有这个参数

exploit 里有一条「512KB 管道载体」路径（`PIPE512`），用来接住被释放的 slab 页。
它的第一步是 `fcntl(fd, F_SETPIPE_SZ, 512*1024)`。

但 Linux 对管道页做**按 uid 记账**：

```
/proc/sys/fs/pipe-user-pages-soft = 16384 页 = 64MB
```

一旦某个 uid 的管道页用量超过这个软上限：

- 新建的 pipe 只给最小容量（2 页 / 8KB）
- **`F_SETPIPE_SZ` 一律返回 `EPERM`（errno=1）**

而 exploit 默认会先预建 20000 个 pipe（`P645_PRE_PIPES=20000`）占住竞态窗口。
20000 个 pipe 早就把 64MB 预算吃光，于是——**512KB 管道载体从未生效过**。

### 直接证据

历史上 62 份真机运行日志里，这一行**无一例外**：

```
v8_pipe first F_SETPIPE_SZ=-1 (want 524288) errno=1
```

设备上跑 `pipetest`（aarch64 静态小程序）复现：

| 已持有 pipe 数 | 新建 pipe 设 512KB |
|---|---|
| 0 | **成功**（524288） |
| 8000 | **EPERM**，且新 pipe 只有 64KB |

## 2. A/B：`PRE_PIPES` 20000 vs 512

- 两臂其余 env 与 App 的 permissive 阶段**逐字相同**（直接调 `./x645`，绕过 UI）
- 交替执行，抵消温度/开机时长漂移；每发前等温度 ≤42°C
- 臂别验证：A 臂日志 `F_SETPIPE_SZ=-1`，B 臂 `=524288` —— 确实走不同代码路径

| 臂 | `PRE_PIPES` | n | 落位成功 | panic |
|---|---|---|---|---|
| A | 20000 | 26 | 16（62%） | 3（12%） |
| B | 512 | 26 | 23（88%） | 1（4%） |

后续又用独立批次复现 `512`（网格 C1 组 + 决赛 F_C1 组，共 20 发）得 **14/20 = 70%**。
合并 `512` 两组：**37/46 = 80%**。两比例 z 检验 `z ≈ 2.0`（双侧 `p ≈ 0.045`）。

**教训**：第一组 88% 里有运气成分；不补第二组就会把结论写成"90%"，实际是 80%。

## 3. 参数网格（每配置 6 发，25–32°C）

| 配置 | 说明 | n | 落位成功 | panic |
|---|---|---|---|---|
| `PIPE512=128` | 管道载体 64→128 条 | 20 | 17（85%） | 2（10%） |
| **基准（`PRE=512`）** 网格组 | — | 6 | 5（83%） | 1（17%） |
| `THRESH=16` | 阈值收紧 | 6 | 5（83%） | 1（17%） |
| `DEL_RUN_MS=1500` | delete 相位缩短 | 6 | 5（83%） | 0 |
| `PRE_PIPES=0` | 完全不预建 | 6 | 5（83%） | 0 |
| `THRESH=64` | 阈值放宽 | 5 | 4（80%） | 0 |
| `PRE_PIPES=2048` | 中间值 | 5 | 4（80%） | 0 |
| `PRE_PIPES=0` + `PIPE512=128` | 组合 | 20 | 13（65%） | 3（15%） |
| `PIPE_K=2` | 喷页系数减半 | 6 | 4（67%） | 1（17%） |
| `ANON2_MB=1536` | anon 喷页 +50% | 6 | 4（67%） | 1（17%） |
| `NDEL=5` | delete 线程 7→5 | 6 | 4（67%） | 1（17%） |

### 三条读出来的规律

1. **`PRE_PIPES` 只有 ≤512 可用**（硬边界，不是调优偏好）：

   | `PRE_PIPES` | `F_SETPIPE_SZ` | 落位 |
   |---|---|---|
   | 0 | 524288 ✓ | 83% |
   | 512 | 524288 ✓ | 86–90% |
   | 2048 | **-1** ✗ | 80% |
   | 20000 | **-1** ✗ | 63% |

   `2048 × 8 页 = 16384`，正好等于软上限，撞得很干脆。

2. **`PIPE512` 64→128 没有增益**（85% vs 86%）。之前的 "6/6 全中" 是小样本运气，
   补到 20 发后回到与基准相同。**不做无依据的改动**。

3. **喷页量存在最优区间**：`PIPE_K=2`（太少，67%）和 `ANON2_MB=1536`（太多，67%）都变差。
   喷得少接不住释放页；喷太猛会挤压管道页预算、拉长窗口。

## 4. 温度的影响（这一项比参数更大）

同一套参数，只改温度：

| 条件 | 落位成功 | panic |
|---|---|---|
| 冷机 25–32°C（本次 A/B，53 发） | 63–90% | **5–6%** |
| 热机 46–48°C（历史 62 份日志） | 37% | **38%** |
| 63°C（历史记录） | 0%（`leak=0`） | — |

结论：**panic 主要是温度驱动，不是参数**。所以 App 里同时做了：

- 严格温度闸（>44°C 先等降温，最多 3 分钟）
- 运行时把屏幕压到最暗（屏幕是 SoC 之外最大的热源，1 档 vs 中高亮差 2–3°C）
- 每发记录 `meta.log`（温度 / 频率 / 充电 / 内存），便于事后归因

## 5. 温度的影响（同一份配置的对照）

人工"温度墙"实验失败了，原因记在下面；但有一对**天然对照**可以说明问题——
同一份配置（`PRE_PIPES=20000`）在两个温度环境下的结果：

| 条件 | n | 落位成功 | panic |
|---|---|---|---|
| 冷机 25–32°C（本次实验） | 26 | **62%** | **12%** |
| 热机 46–48°C（历史 62 份运行日志，同为 `PRE_PIPES=20000`） | 62 | 50% | **37%** |

结论：**panic 主要由温度驱动，不是参数**。参数只把落位率从 62% 拉到 80%，温度把 panic 从 12% 推到 37%。
所以产品上最该做的不是继续调 exploit，而是：

- 严格温度闸（>44°C 先等降温）
- 运行时把屏幕压到最暗（屏幕是 SoC 之外最大热源）
- 每发记录 `meta.log`（温度/频率/充电/内存），便于事后归因

### 为什么没做成人造温度墙

三次尝试都失败，记下来避免重复：

1. **想精确控温在 44°C：做不到。** `thermal_zone0`（cpullc）对负载响应极快——
   8 线程忙等 1 秒就能从 27°C 冲到 48°C，6 秒能到 61°C。任何"先升温再开打"的方案
   都会冲过头。
2. **想用"先升温、再开打"的两段式：中间温度会掉。** 升温后到真正 `execve` 之间隔着
   十几次 adb 往返（约 10 秒），实测温度从 50°C 掉回 33°C。
3. **背靠背连打 20 发：温度根本没升起来。** 散热器在岗时，每发 50 秒的负载只让机身
   停在 25–30°C，20 发全程没进过 40°C。

另外发现一个测量陷阱：**设备刚重启后的 1–2 分钟内，温度读数是假的**——
实测读到 `t0=84°C / die=81°C`，而同一时刻实际机体只有 27°C。
排热数据时必须丢弃 `uptime < 120s` 的样本。

## 6. 方法与可复现

设备端直接调用原生载荷（与 App 同一套 env，只是绕过 UI）：

```bash
cd /data/local/tmp/rk && env \
  P645_STAGE=1 P645_STAGE_FROM=0 P645_STAGE_TO=1 P645_STAGE_TRIES=4 P645_ATTEMPTS=1 \
  P645_TIMERS=54000 P645_REPEATS=520 P645_NDEL=7 P645_DEL_RUN_MS=2500 \
  P645_CONC=1 P645_ANON_MB=8 P645_FREEZE=1 P645_V8=1 P645_ANON2_MB=1024 \
  P645_PIPE512=64 P645_PIPE_K=4 P645_MODE=4 P645_THRESH=32 P645_SCAN_STOP=1 \
  P645_FORCE_LEFT=0xffffff8049fe7a59 \
  P645_PRE_PIPES=512 P645_LOG=/data/local/tmp/rk/ab.log \
  ./x645
```

判定（读日志尾部）：

| 日志尾部 | 归类 |
|---|---|
| `stage_all_done` + `leak=0x…` | 落位成功 |
| `stage_all_done` + `leak=0` / `stage0_failed_no_leak` | 未命中 |
| `v8_reaping victim=…` 之后无输出 | panic（kill 相位） |
| `concurrent spray start …` 之后无输出 | panic（喷页相位） |

跑完脚本会 `setenforce 1` 复位 SELinux，保持两臂条件一致。
每轮记录温度、`F_SETPIPE_SZ` 返回值、充电状态与 CPU 频率。

## 7. 一个必须记住的坑

`F_SETPIPE_SZ` 的 EPERM **不会报错到 UI**，只会让载体静默退化成 8KB 小管道。
如果没有对着 `v8_pipe first F_SETPIPE_SZ=` 这一行做核对，很容易把它当"正常现象"，
然后再去调其他参数——方向从一开始就是错的。
